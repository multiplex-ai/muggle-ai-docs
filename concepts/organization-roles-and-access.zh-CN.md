# 组织角色与项目访问权限

本页说明组织成员身份如何转化为对组织所拥有项目的访问权限，以及在你需要审计权限时，Muggle Test 如何回答“为什么这个人在这个项目上拥有那个角色？”这一问题。

如果你刚接触企业组织，请先阅读[企业组织](billing/enterprise-organizations.md)——本页假定你已经了解什么是组织、席位如何运作，以及个人账单与组织账单的区别。

## 为何需要本页

组织内的访问权限不止有一个来源：

- 你可能被直接邀请加入某个特定项目。
- 你可能属于某个已获得项目访问权限的团队。
- 你可能创建了该项目，因此成为它的隐式所有者。
- 你可能是拥有该项目的组织的成员；在这种情况下，你的组织角色会让你在该组织拥有的每个项目上都获得基础级别的访问权限。

当其中多项同时成立时，Muggle Test 会将它们解析为此人在该项目上的单一**实际角色**。本页介绍这一解析过程如何运作，让你无需猜测就能推断团队的访问权限。

## 组织角色一览

组织有三种角色：

| 组织角色 | 定位 |
| :--- | :--- |
| **所有者** | 掌管整个组织。掌控账单，可以邀请和移除任何人，对每个组织项目拥有完全控制权。 |
| **管理员** | 日常运营者。管理成员和项目，但不接触账单，也不能直接删除项目。 |
| **成员** | 普通组织用户。可以在已获得访问权限的项目中工作，并默认对每个组织项目拥有只读可见性。 |

参阅[企业组织 → 角色](billing/enterprise-organizations.md)，了解组织层级的完整能力矩阵（谁可以邀请成员、谁可以管理账单等）。

## 组织角色如何逐级传递到项目

组织拥有的每个项目，都会根据该组织每位已激活成员的组织角色，自动授予其一个基础项目角色：

| 如果你的组织角色是…… | ……你会自动在该组织拥有的每个项目上获得此角色 |
| :--- | :--- |
| 所有者 | 项目**所有者**——完全控制权，包括删除项目等破坏性操作 |
| 管理员 | 项目**维护者**——可以编辑项目、管理运行、管理测试用例和管理协作者，但不能删除项目，也不能将其转出组织 |
| 成员 | 项目**查看者**——可以查看项目及其运行和报告，但不能做任何更改 |

简要说明理由：

- **所有者**为组织付费。他们永远不应被挡在组织拥有的任何东西之外。
- **管理员**负责运营。他们需要广泛的写入权限，但不应该能够把项目带走，或者在状态不佳的某天把它删掉。
- **成员**是默认角色。他们可以看到组织正在做什么，但让新员工在入职第一天就成为每个项目的编辑者，通常并不是你想要的。写入权限应当有意识地授予。

这一级联是固定策略——不能按组织重新配置。在所有组织中保持一致的级联，比为每个客户量身定制权限矩阵更容易解释、更容易审计，也更容易提供支持。如果有级联未覆盖的具体权限需求，正确的做法是在该特定项目上为此人授予直接角色。

## 叠加：级联与直接授权

级联是底线，而不是上限。项目成员还可以获得**直接**项目角色——例如，所有者或管理员将其以**编辑者**身份添加到某个特定项目。

当级联和直接授权同时适用时，Muggle Test 会取两者中**较高**的那个。直接授权永远不会降低用户的角色。

三个简单示例：

1. **在一个项目上提升成员的角色。** Priya 是组织的成员（级联：查看者）。她负责结账流程的重写，因此一位管理员在 `checkout-flow-tests` 项目上授予她直接的**编辑者**角色。她在这个项目上的实际角色变为**编辑者**。她在其他所有组织项目上的角色仍通过级联保持为查看者。

2. **冗余授权无害。** Diego 是组织的管理员（级联：维护者）。另有人也将他作为直接**编辑者**添加到某个特定项目。他在该项目上的实际角色仍是**维护者**，因为级联角色更高。这项直接授权实际上不起作用，但也不会造成任何问题。

3. **团队授权同样计入。** Alex 是成员（级联：查看者）。他所在的团队已获得 `landing-page-tests` 项目的**编辑者**访问权限。他在该项目上的实际角色是**编辑者**，来自团队授权。

无论有多少来源参与，同样的“取最高者”规则都适用。一个级联角色为查看者、团队授权为编辑者、直接授权为维护者的用户，最终角色为**维护者**。

## 访问权限的来源

组织项目上的角色可能来自四个地方。这一点很重要，因为下文的[实际角色查询](#looking-up-someones-effective-role)会分别返回每个来源。

| 来源 | 含义 |
| :--- | :--- |
| **直接** | 有人以特定角色将此用户明确添加到此项目。 |
| **团队** | 用户属于某个团队，且该团队已在此项目上获得某个角色。 |
| **所有者** | 用户创建了此项目，因此是它的隐式所有者。 |
| **组织** | 项目属于某个组织，且此用户是该组织的成员。此处的角色由上文所述的级联决定。 |

用户在项目上的**实际角色**，是所有适用来源中最高的那个角色，无论适用的来源有几个。如果都不适用，该用户就无法访问此项目。

## 查询某人的实际角色

组织所有者和管理员可以查询任何成员在组织拥有的任何项目上的实际角色，并查看各来源参与情况的完整明细。

该查询通过 API 提供；控制台目前还没有对应的页面：

```
GET /v1/protected/organizations/{orgId}/projects/{projectId}/effective-role/{userId}
```

它返回：

- **实际角色。** 此人尝试在此项目上执行操作时，实际生效的那个唯一角色。
- **参与来源。** 为此人授予角色的每个来源（直接、团队、所有者、组织）的列表，以及每个来源授予的角色。如果该用户没有访问权限，列表为空。

### 何时使用实际角色视图

| 你想要…… | ……实际角色视图能帮上忙，因为它会显示 |
| :--- | :--- |
| 弄清新员工为什么已经对每个项目都有查看者权限 | 通过级联授予查看者角色的**组织**来源 |
| 确认外包人员只能访问他们应当访问的那一个项目 | 预期项目上的**直接**授权，且其他任何项目上都没有来源 |
| 弄清团队成员离开团队后为什么仍能编辑项目 | 移出团队时未受影响的剩余**直接**或**组织**来源 |
| 核实项目所有者确实是你预期的用户 | **所有者**来源 |
| 排查队友报告的“权限被拒绝”问题 | **空**的来源列表，或低于该操作所需级别的角色 |

### 注意事项

- **这是只读查询。** 它只显示当前的实际情况。更改访问权限仍需通过项目成员管理和**组织 → 成员**进行。
- **该视图需要特权。** 由于它会暴露他人的访问权限，只有组织管理员和所有者才能看到。普通成员无法查询彼此的角色。
- **它不能跨组织。** 一个组织的管理员无法使用该查询探查另一个组织拥有的项目，即使他们恰好知道该项目的标识符。组织以外的项目会报告为未找到。
- **它与系统实际执行的规则一致。** 查询返回的实际角色，正是由用户尝试运行工作流或编辑测试用例时把关访问的同一套规则计算得出。不存在“仅供调试”的捷径——如果查询显示某人是维护者，那么他在任何地方都是维护者。

## 在组织内创建项目

当你在组织上下文中创建项目时，可以将该项目关联到该组织，使其继承本页所述的一切：组织的账单，以及从组织角色到项目角色的级联。

要在创建时将项目关联到组织：

- 你必须是该组织的已激活成员（所有者、管理员或成员）。尚未接受邀请或已被停用的成员，无法在名义上“所属”的组织下创建项目。
- 你必须在该组织中至少拥有**成员**角色。换句话说，任何已激活的组织成员都可以创建组织项目——创建权限并不仅限于所有者和管理员，也没有可以对此加以限制的设置。

个人项目之后也可以按照相同的成员资格规则移入组织。这一迁移是单向的。

项目归属组织后：

- **所有权是永久的。** 你无法将组织项目移回个人所有，也无法将其从一个组织移到另一个组织。这是一项有意的限制，确保在项目的整个生命周期中，每一张账单和每一条审计日志都有明确的所有者。如果你需要“移动”组织项目，请在新的所有者名下重新创建它。
- **级联立即生效。** 组织的每位现有成员会在新项目创建的那一刻获得其级联角色。未来的成员会在其邀请被接受的那一刻获得该角色。
- **账单计入组织钱包。** 针对该项目的工作流运行会从组织的钱包扣费，而不是从创建者的个人钱包扣费。完整说明请参阅[企业组织 → 个人账单与组织账单](billing/enterprise-organizations.md)。
