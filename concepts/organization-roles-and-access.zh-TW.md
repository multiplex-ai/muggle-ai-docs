# 組織角色與專案存取權限

本頁說明組織成員身分如何轉換成對組織所擁有專案的存取權限，以及當你需要稽核權限時，Muggle Test 如何回答「為什麼這個人在這個專案上擁有那個角色？」這個問題。

如果你剛接觸企業組織，請先閱讀[企業組織](billing/enterprise-organizations.md)——本頁假設你已經知道什麼是組織、席位如何運作，以及個人帳單與組織帳單的差別。

## 本頁的用途

組織內的存取權限不只來自一個地方：

- 你可能直接受邀加入某個特定專案。
- 你可能隸屬於某個已獲得專案存取權限的團隊。
- 你可能建立了該專案，因此成為它的隱含擁有者。
- 你可能是擁有該專案之組織的成員；在這種情況下，你的組織角色會讓你在該組織擁有的每個專案上都獲得基本層級的存取權限。

當其中多項同時成立時，Muggle Test 會將它們解析為此人在該專案上的單一**實際角色**。本頁說明這個解析過程如何運作，讓你不必猜測就能推斷團隊的存取權限。

## 組織角色一覽

組織有三種角色：

| 組織角色 | 定位 |
| :--- | :--- |
| **擁有者** | 掌管整個組織。掌控帳單，可以邀請及移除任何人，對每個組織專案擁有完整控制權。 |
| **管理員** | 日常營運者。管理成員與專案，但不碰帳單，也無法直接刪除專案。 |
| **成員** | 一般組織使用者。可以在已獲得存取權限的專案中工作，並預設對每個組織專案擁有唯讀的檢視權限。 |

請參閱[企業組織 → 角色](billing/enterprise-organizations.md)，了解組織層級的完整功能矩陣（誰可以邀請成員、誰可以管理帳單等）。

## 組織角色如何向下套用到專案

組織擁有的每個專案，都會依據該組織每位已啟用成員的組織角色，自動授予對方一個基本專案角色：

| 如果你的組織角色是…… | ……你會自動在該組織擁有的每個專案上獲得這個角色 |
| :--- | :--- |
| 擁有者 | 專案**擁有者**——完整控制權，包括刪除專案等破壞性操作 |
| 管理員 | 專案**維護者**——可以編輯專案、管理執行、管理測試案例及管理協作者，但無法刪除專案，也無法將專案移出組織 |
| 成員 | 專案**檢視者**——可以檢視專案及其執行與報告，但無法做任何變更 |

簡單說明背後的考量：

- **擁有者**為組織付費。他們永遠不該被擋在組織擁有的任何東西之外。
- **管理員**負責營運。他們需要廣泛的寫入權限，但不應該能把專案帶走，或在狀況不好的某一天把它刪掉。
- **成員**是預設角色。他們可以看到組織正在進行哪些工作，但讓新進員工在到職第一天就成為每個專案的編輯者，通常不是你想要的結果。寫入權限應該經過深思熟慮再授予。

這套向下套用機制是固定政策——無法依組織重新設定。在所有組織中維持一致的向下套用規則，比為每位客戶量身打造權限矩陣更容易解釋、更容易稽核，也更容易提供支援。如果有向下套用規則未涵蓋的具體權限需求，正確的做法是在該特定專案上為此人授予直接角色。

## 疊加：向下套用與直接授權

向下套用的角色是底線，而不是上限。專案成員也可以獲得**直接**專案角色——例如，擁有者或管理員將對方以**編輯者**身分加入某個特定專案。

當向下套用的角色與直接授權同時適用時，Muggle Test 會取兩者中**較高**的那個。直接授權絕不會調降使用者的角色。

三個簡單範例：

1. **在單一專案上提升成員的角色。** Priya 是組織的成員（向下套用：檢視者）。她負責結帳流程的改寫，因此一位管理員在 `checkout-flow-tests` 專案上授予她直接的**編輯者**角色。她在這個專案上的實際角色變成**編輯者**。她在其他所有組織專案上的角色，仍因向下套用而維持為檢視者。

2. **重複授權並無害處。** Diego 是組織的管理員（向下套用：維護者）。另外有人也將他以直接**編輯者**身分加入某個特定專案。他在該專案上的實際角色仍是**維護者**，因為向下套用的角色比較高。這項直接授權實際上沒有作用，但也不會造成任何問題。

3. **團隊授權同樣列入計算。** Alex 是成員（向下套用：檢視者）。他所屬的團隊已獲得 `landing-page-tests` 專案的**編輯者**存取權限。他在該專案上的實際角色是**編輯者**，來自團隊授權。

無論有多少個來源，都適用同樣的「取最高者」規則。向下套用為檢視者、團隊授權為編輯者、直接授權為維護者的使用者，最終角色是**維護者**。

## 存取權限的來源

組織專案上的角色可能來自四個地方。這點很重要，因為下方的[實際角色查詢](#looking-up-someones-effective-role)會分別傳回每個來源。

| 來源 | 意義 |
| :--- | :--- |
| **直接** | 有人以特定角色將此使用者明確加入此專案。 |
| **團隊** | 使用者隸屬於某個團隊，而該團隊已在此專案上獲得某個角色。 |
| **擁有者** | 使用者建立了此專案，因此是它的隱含擁有者。 |
| **組織** | 專案屬於某個組織，而此使用者是該組織的成員。此處的角色取決於上述的向下套用規則。 |

使用者在專案上的**實際角色**，是所有適用來源中最高的角色，不論適用的來源有幾個。如果都不適用，該使用者就無法存取此專案。

## 查詢某人的實際角色

組織擁有者與管理員可以查詢任何成員在組織擁有的任何專案上的實際角色，並查看各來源的完整明細。

此查詢透過 API 提供；儀表板目前還沒有對應的畫面：

```
GET /v1/protected/organizations/{orgId}/projects/{projectId}/effective-role/{userId}
```

它會傳回：

- **實際角色。** 此人嘗試在此專案上執行操作時，實際生效的那一個角色。
- **貢獻來源。** 列出每個授予此人角色的來源（直接、團隊、擁有者、組織），以及各來源授予的角色。如果該使用者沒有存取權限，清單會是空的。

### 實際角色檢視的使用時機

| 你想要…… | ……實際角色檢視之所以有幫助，是因為它會顯示 |
| :--- | :--- |
| 了解新進員工為什麼已經對每個專案都有檢視者權限 | 透過向下套用授予檢視者角色的**組織**來源 |
| 確認約聘人員只能存取他們該存取的那一個專案 | 預期專案上的**直接**授權，且其他專案都沒有任何來源 |
| 弄清楚團隊成員離開團隊後為什麼仍能編輯專案 | 移出團隊時未受影響、仍然存在的**直接**或**組織**來源 |
| 確認專案擁有者確實是你預期的使用者 | **擁有者**來源 |
| 排解隊友回報的「權限遭拒」問題 | **空白**的來源清單，或低於該操作所需等級的角色 |

### 注意事項

- **這是唯讀查詢。** 它只會顯示目前的實際狀態。變更存取權限仍然要透過專案成員管理與**組織 → 成員**進行。
- **此檢視需要特殊權限。** 由於它會揭露他人的存取權限，只有組織管理員與擁有者才能看到。一般成員無法查詢彼此的角色。
- **它無法跨組織使用。** 某個組織的管理員無法用這項查詢探查其他組織擁有的專案，即使他們剛好知道該專案的識別碼也一樣。組織以外的專案會回報為找不到。
- **它與系統實際執行的規則一致。** 查詢傳回的實際角色，正是由使用者嘗試執行工作流程或編輯測試案例時把關存取的同一套規則計算而來。沒有「僅供偵錯」的捷徑——如果查詢顯示某人是維護者，那麼他在任何地方都是維護者。

## 在組織內建立專案

當你在組織環境下建立專案時，可以將該專案與該組織建立關聯，讓它繼承本頁所述的一切：組織的帳單，以及從組織角色到專案角色的向下套用。

若要在建立時將專案與組織建立關聯：

- 你必須是該組織的已啟用成員（擁有者、管理員或成員）。尚未接受邀請或已遭停用的成員，無法在名義上「所屬」的組織底下建立專案。
- 你在該組織中至少必須擁有**成員**角色。換句話說，任何已啟用的組織成員都能建立組織專案——建立權限並不限於擁有者與管理員，也沒有任何設定可以加以限制。

個人專案之後也可以依照相同的成員資格規則移入組織。這項移轉是單向的。

專案歸屬於組織之後：

- **所有權是永久的。** 你無法將組織專案移回個人擁有，也無法將它從一個組織移到另一個組織。這是刻意設下的限制，確保在專案的整個生命週期中，每一張帳單與每一筆稽核記錄都有明確的擁有者。如果你需要「移動」組織專案，請在新的擁有者名下重新建立。
- **向下套用立即生效。** 組織的每位現有成員會在新專案建立的那一刻獲得向下套用的角色。未來的成員則會在邀請被接受的那一刻獲得該角色。
- **帳單由組織錢包支付。** 針對該專案執行的工作流程會從組織的錢包扣款，而不是從建立者的個人錢包扣款。完整說明請參閱[企業組織 → 個人帳單與組織帳單](billing/enterprise-organizations.md)。
