# 账单暂停与恢复

定期付款失败时，企业组织会被暂停，直到账单付清为止。以下是相关规则——让所有者清楚知道会发生什么，也让突然看到“Organization is suspended”（组织已暂停）错误的管理员和成员明白发生了什么、该如何处理。

如需了解一般账单信息，请参阅[企业组织](billing/enterprise-organizations.md)了解席位和定价的运作方式，并参阅[订阅套餐](billing/subscription-plans.md)了解企业版与其他套餐的对比。

## 为什么会有暂停机制

组织通过 Stripe 为两项内容付费：席位订阅（按席位定期收费，每月计费）和 Token 用量（按量计量，在下一张发票中结算）。付款可能因为一些常见原因失败——银行卡过期、银行拒绝交易、账单地址不匹配——而 Muggle Test 必须决定在账户未付款期间如何处理。

规则刻意保持简单：**发票付款失败时，组织会被立即暂停**。没有宽限期，没有降级服务期，在关闭访问之前也没有温和的预警。

我们做出这一选择有三个原因：

1. **可预测性**。暂停是一种明确的二元状态。你要么完全正常运行，要么完全被暂停。不存在“部分功能可用、部分功能不可用”的中间状态，运维团队也不必在每个支持工单中解释这种状态。
2. **如实归属成本**。为未支付账单的账户继续提供服务，意味着由其他人承担成本。要让产品定价保持真实合理，最简单的方式就是在账单停止支付的那一刻停止计量。
3. **促使快速解决**。与悄无声息的服务降级相比，一次短暂而明显的中断更有可能让人在接下来五分钟内更新银行卡。暂停机制的设计目标就是让人立刻察觉、立刻能够解决。

## “已暂停”的实际含义

当 Stripe 通知 Muggle Test 某个组织的定期付款失败时，会同时发生三件事：

1. **组织被切换为暂停状态**。在账单付清之前，该组织被视为不可用。
2. **每位已激活的所有者都会收到催缴邮件**。邮件会注明组织名称，并说明付款失败。管理员和成员不会收到邮件，因为我们认为账单由所有者负责，向更多人群发只会增加干扰。
3. **组织范围内的 API 调用和工作流会被拒绝**。在组织暂停期间，任何需要组织上下文的请求——在组织项目上运行工作流、编辑组织项目的测试用例、邀请新成员、更改设置——都会被阻止，并返回明确的错误。

被阻止的请求会返回禁止访问（forbidden）响应，消息为：**“Organization is suspended.”**（组织已暂停。）这是成员和管理员最可能首先看到的错误，也是提醒所有者处理账单问题的信号。

### 暂停期间仍可使用的功能

任何具有成员身份的人仍可在控制台中打开该组织，并看到它已被暂停。否则，被暂停的组织会直接从控制台中“消失”，没人知道该去找谁。

个人项目和个人账户完全不受影响。如果 Alice 是某个已暂停组织的成员，她的个人项目、个人钱包以及她所属的其他任何组织都会继续正常运行。只有被暂停的组织会受到限制。

### 被阻止的操作

其他所有需要组织上下文的操作都会被阻止，包括但不限于：

| 功能 | 暂停期间是否被阻止？ |
| :--- | :--- |
| 读取组织记录 | **否，仍然允许**（以便你看到问题） |
| 在组织项目上运行工作流 | 是 |
| 创建、编辑或删除组织项目 | 是 |
| 在组织项目上创建、编辑或删除测试用例或用户旅程 | 是 |
| 邀请新成员或更改成员角色 | 是 |
| 查看组织项目的成本和用量报告 | 是 |
| 使用组织的共享 Token 钱包 | 是 |
| 任何成员的个人项目 | **不会被阻止**（个人账户相互独立） |

## 催缴：如何通知你

催缴（dunning）是指通知客户付款失败、并为其提供解决途径的流程。Muggle Test 的催缴机制刻意保持精简。

- **谁会收到邮件**。组织的每位已激活所有者都会收到催缴邮件。已被停用或移除的所有者不会收到邮件。管理员和成员完全不会收到邮件。
- **邮件内容**。邮件会注明组织名称，并确认一笔由 Stripe 安排的定期付款失败。
- **发送频率**。每次付款失败事件只发送一次邮件——而不是 Stripe 每重试一次就发送一次。作为其自身催缴计划的一部分，Stripe 可能会在几天内多次重试同一张失败的发票；Muggle Test 会在订阅历史中记录每次尝试，但不会在每次重试时再次给所有者发邮件。收到一封邮件就意味着“需要采取行动”，而不是“这已是同一警报的第四份副本”。
- **邮件不会做的事**。邮件不包含敏感的账单详情，不会尝试直接在邮件中收款，也不会索要凭据。

### 为什么没有宽限期

新的企业客户经常问：“能否在关闭访问之前给我们 24 或 48 小时？”答案是否定的：

对于没有关注邮件的人来说——几乎在任何时刻，团队中的绝大多数人都是如此——宽限期与正常运行状态毫无区别。等到宽限期结束、组织真正被锁定时，实际使用产品的人不得不在工作进行到一半时放下手头的事。立即中断虽然更生硬，但问题也会解决得快得多，因为遇到中断的人可以直接向所有者反映。

如果对某个客户而言，更长的通知期确实很重要，请向销售团队提出。

## 自动恢复

恢复完全自动进行。没有“取消暂停”按钮，也不需要提交支持工单。

Stripe 会按自己的计划重试失败的发票。当其中某次重试成功时——无论是在失败一小时后还是几天后——组织都会立即恢复为正常状态。所有被阻止的路由会同时解除限制，共享钱包重新可用，成员和所有者的操作也会完全恢复到暂停之前的状态。

恢复步骤是幂等的：

- **如果组织处于暂停状态**，它会被重新激活，并记录一条审计条目，说明此次重新激活是由一笔成功的 Stripe 付款触发的，而不是由人工操作员触发的。
- **如果组织本来就处于正常状态**——每一笔例行、正常的月度付款都属于这种情况——则什么也不会发生。该事件只是确认最新的发票已按时支付。

需要了解的几个细节：

- **不会发送恢复邮件**。所有者在付款失败时已经收到了催缴邮件，而产品恢复正常本身就说明了一切。
- **暂停绝不会停用成员**。在整个暂停期间，他们的席位仍分配给他们。组织一恢复，他们就可以继续工作，无需重新邀请或重新启用。
- **待处理的邀请不会被撤销**。暂停之前有效的邀请在恢复后仍然有效，除非在此期间已超过常规的 7 天有效期。

## 解决暂停问题

控制台目前还没有组织账单页面。只要 Stripe 的某次自动重试成功，组织就会自动恢复为正常状态，被阻止的操作也会立即恢复可用。

如果银行卡持续付款失败，而你需要更换支付服务商，请联系 [sales@muggle-ai.com](mailto:sales@muggle-ai.com)，工作人员会协助你解决。

## 席位数量与账单

对组织所做的席位变更会先按比例计费应用到订阅，然后再应用到组织。

你实际会注意到的影响是邀请上限。当已激活成员和待处理邀请占满所有席位时，新的邀请会被拒绝，并显示“No available seats. Purchase more seats to invite new members.”（没有可用席位。请购买更多席位以邀请新成员。）请撤销不再需要的邀请，或新增席位。

暂停不会改变席位数量，也不会释放席位。组织被暂停时处于已激活状态的成员仍计入席位上限，这是有意为之：他们仍属于该组织，并会在账单恢复的那一刻完全恢复使用。
