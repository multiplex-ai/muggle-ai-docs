# 帳單停權與恢復

排定的付款失敗時，企業組織會遭到停權，直到帳單付清為止。以下是相關規則——讓擁有者確切知道會發生什麼事，也讓突然看到「Organization is suspended」（組織已停權）錯誤的管理員與成員了解狀況，並知道該怎麼處理。

如需一般帳單資訊，請參閱[企業組織](billing/enterprise-organizations.md)了解席位與定價的運作方式，並參閱[訂閱方案](billing/subscription-plans.md)了解企業版與其他方案的比較。

## 為什麼要停權

組織透過 Stripe 支付兩項費用：席位訂閱（依席位定期收費，按月計費）與 Token 用量（計量計費，在下一張發票中結算）。付款可能因為一些常見原因而失敗——信用卡過期、銀行拒絕交易、帳單地址不符——而 Muggle Test 必須決定在帳戶未付款期間該如何處理。

規則刻意設計得很簡單：**發票付款失敗時，組織會立即遭到停權**。沒有寬限期、沒有降級服務期，在關閉存取之前也沒有溫和的預警。

我們這樣決定有三個原因：

1. **可預測性**。停權是明確的二元狀態。你要麼完全正常運作，要麼完全遭到停權。不存在「部分功能可用、部分功能不可用」的中間狀態，維運團隊也不必在每張支援工單中解釋這種狀態。
2. **如實歸屬成本**。替未支付帳單的帳戶繼續提供服務，等於讓其他人承擔成本。要讓產品定價維持誠實合理，最簡單的方式就是在帳單停止支付的那一刻停止計量。
3. **促使迅速解決**。比起悄無聲息的服務降級，一次短暫而明顯的中斷更有可能讓人在接下來五分鐘內更新信用卡。停權機制的設計目標，就是讓人立刻察覺、也能立刻解決。

## 「已停權」的實際意義

當 Stripe 通知 Muggle Test 某個組織的排定付款失敗時，會同時發生三件事：

1. **組織會切換為停權狀態**。在帳單付清之前，該組織會被視為無法使用。
2. **每位已啟用的擁有者都會收到催繳電子郵件**。電子郵件會註明組織名稱，並說明付款失敗。管理員與成員不會收到電子郵件，因為我們認為帳單是擁有者的責任，寄給更多人只會增加干擾。
3. **組織範圍內的 API 呼叫與工作流程會遭到拒絕**。在組織停權期間，任何需要組織情境的請求——在組織專案上執行工作流程、編輯組織專案的測試案例、邀請新成員、變更設定——都會遭到封鎖，並傳回明確的錯誤。

遭到封鎖的請求會傳回禁止存取（forbidden）回應，訊息為：**「Organization is suspended.」**（組織已停權。）這是成員與管理員最可能最先看到的錯誤，也是提醒擁有者處理帳單問題的訊號。

### 停權期間仍可使用的功能

任何具有成員身分的人仍可在儀表板中開啟該組織，並看到它已遭到停權。若非如此，遭到停權的組織就會直接從儀表板上「消失」，也就沒有人知道該去找誰。

個人專案與個人帳戶完全不受影響。如果 Alice 是某個已停權組織的成員，她的個人專案、個人錢包，以及她所屬的其他任何組織都會繼續正常運作。只有遭到停權的組織會受到限制。

### 會遭到封鎖的操作

其他所有需要組織情境的操作都會遭到封鎖，包括但不限於：

| 功能 | 停權期間是否遭到封鎖？ |
| :--- | :--- |
| 讀取組織記錄 | **否，仍可使用**（讓你能看到問題） |
| 在組織專案上執行工作流程 | 是 |
| 建立、編輯或刪除組織專案 | 是 |
| 在組織專案上建立、編輯或刪除測試案例或使用者旅程 | 是 |
| 邀請新成員或變更成員角色 | 是 |
| 查看組織專案的成本與用量報告 | 是 |
| 使用組織的共用 Token 錢包 | 是 |
| 任何成員的個人專案 | **不會遭到封鎖**（個人帳戶彼此獨立） |

## 催繳：如何通知你

催繳（dunning）是指通知客戶付款失敗，並提供解決途徑的流程。Muggle Test 的催繳機制刻意保持精簡。

- **誰會收到電子郵件**。組織的每位已啟用擁有者都會收到催繳電子郵件。已停用或已移除的擁有者不會收到。管理員與成員完全不會收到電子郵件。
- **電子郵件的內容**。電子郵件會註明組織名稱，並確認一筆由 Stripe 排定的付款已失敗。
- **寄送頻率**。每次付款失敗事件只會寄送一次電子郵件——而不是 Stripe 每重試一次就寄一次。依照 Stripe 自身的催繳排程，它可能會在數天內多次重試同一張失敗的發票；Muggle Test 會在訂閱記錄中記下每次嘗試，但不會在每次重試時再寄電子郵件給擁有者。收到一封電子郵件代表「需要採取行動」，而不是「這已經是同一則警示的第四份副本」。
- **電子郵件不會做的事**。電子郵件不含敏感的帳單詳細資料，不會試圖直接在信中收款，也不會要求提供憑證。

### 為什麼沒有寬限期

新的企業客戶常問：「能不能在關閉存取之前給我們 24 或 48 小時？」答案是不行：

對於沒有在看電子郵件的人來說——在任何時刻，團隊中幾乎每個人都是如此——寬限期與正常運作狀態根本沒有差別。等到寬限期結束、組織真正遭到鎖定時，實際使用產品的人就不得不在工作進行到一半時放下手邊的事。立即中斷雖然比較生硬，但問題也會解決得快得多，因為遇到中斷的人可以直接向擁有者反映。

如果對特定客戶而言，較長的通知期確實很重要，請向業務團隊提出。

## 自動恢復

恢復完全自動進行。沒有「解除停權」按鈕，也不需要提交支援工單。

Stripe 會依自己的排程重試失敗的發票。當其中某次重試成功時——無論是在失敗一小時後，還是數天之後——組織都會立即恢復為正常狀態。所有遭到封鎖的路由會同時解除限制，共用錢包重新可用，成員與擁有者的操作也會完全恢復到停權之前的狀態。

恢復步驟具有冪等性：

- **如果組織處於停權狀態**，它會重新啟用，並留下一筆稽核記錄，註明此次重新啟用是由一筆成功的 Stripe 付款觸發，而不是由人工操作員觸發。
- **如果組織原本就處於正常狀態**——每一筆例行、正常的每月付款都屬於這種情況——就不會發生任何事。該事件只是確認最新的發票已準時付清。

幾個值得了解的細節：

- **不會寄送恢復電子郵件**。擁有者在付款失敗時已經收到催繳電子郵件，而產品恢復正常運作本身就說明了一切。
- **停權絕不會停用成員**。在整個停權期間，他們的席位仍分配給他們。組織一恢復，他們就能繼續工作，不必重新邀請或重新啟用。
- **尚待接受的邀請不會遭到撤銷**。停權前有效的邀請在恢復後依然有效，除非這段期間已超過一般的 7 天期限。

## 解決停權問題

儀表板目前還沒有組織帳單頁面。只要 Stripe 的某次自動重試成功，組織就會自行恢復為正常狀態，遭到封鎖的操作也會立即恢復可用。

如果信用卡持續付款失敗，而你需要更換付款服務商，請聯絡 [sales@muggle-ai.com](mailto:sales@muggle-ai.com)，工作人員會協助你處理。

## 席位數量與帳單

對組織所做的席位變更會先按比例計費套用到訂閱，然後再套用到組織。

你實際會注意到的影響是邀請上限。當已啟用成員與尚待接受的邀請占滿所有席位時，新的邀請會遭到拒絕，並顯示「No available seats. Purchase more seats to invite new members.」（沒有可用的席位。請購買更多席位以邀請新成員。）請撤銷不再需要的邀請，或新增席位。

停權不會改變席位數量，也不會釋出席位。組織遭到停權時處於已啟用狀態的成員仍會計入席位上限，這是刻意的設計：他們仍屬於該組織，並會在帳單恢復的那一刻完全恢復使用。
